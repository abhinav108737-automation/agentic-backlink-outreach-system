# CCR-004 — configurable follow-up scheduling and sending window (C2)

Status: **APPROVED by the user (2026-10-25), EXECUTED.**
Affects contract **C2** (`PolicyBody`). Contract version `0.3.0` → `0.4.0`.
Migration: **none required.** New API surface: **none.**

## What

Add five fields to the frozen `kb_contracts.domain.PolicyBody`:

| Field | Default | Meaning |
|---|---|---|
| `follow_up_delays_days` | `(4, 7)` | days after the previous *successful* send before each follow-up step. Element 0 is the delay after the initial send; element 1 the delay after the first follow-up. |
| `send_window_hours` | `24` | the rolling window for `daily_send_limit`, `per_domain_send_limit` and `per_contact_send_limit`. |
| `timezone` | `"UTC"` | IANA name used to interpret the sending window. |
| `sending_window_start_hour` | `0` | local hour, inclusive. |
| `sending_window_end_hour` | `24` | local hour, exclusive. `0..24` with start < end; `0..24` means "no restriction". |

A `model_validator` enforces: every delay strictly positive; `len(follow_up_delays_days) >=
max_follow_ups` so a configured follow-up always has a delay; `0 <= start < end <= 24`;
`send_window_hours >= 1`; and a timezone that actually resolves via `zoneinfo`.

## Why

`max_follow_ups` existed from the Foundation Gate but the *interval* had nowhere to live, so
Wave 2A could enqueue `outreach.follow_up` without being able to say when it was due. Lane B
declined to invent a delay and so did the Lead; this CCR is that decision being made properly
rather than defaulted into the code.

## The 24-hour send window is NOT being grandfathered

Wave 2A enforced the three send limits over a rolling 24 hours via a module constant
(`SEND_WINDOW`). **That was a Lead default, not an approved business rule**, and it was
reported as such at the Wave 2A checkpoint. This CCR does not retroactively bless it: it moves
the value into `PolicyBody.send_window_hours` where it is visible, versioned and configurable
per campaign. The default remains 24 only so behaviour does not change silently under existing
seeded policies. Choosing a different window is now a policy edit, not a code edit.

## Behavioural requirements this CCR carries

These are contract-adjacent and are implemented against it:

1. At most `max_follow_ups` follow-ups (default 2); an existing stricter campaign policy wins.
2. Each delay is measured from the previous **successful** send, not from scheduling time.
3. Follow-ups stop on: reply, opt-out, bounce, suppression, campaign pause, kill switch.
4. Policy, approval, idempotency and sender eligibility are re-evaluated **immediately before
   dispatch**, not only at enqueue — a suppression or pause landing in between must still stop it.
5. A dispatch falling outside the sending window is deferred to the next in-window moment in the
   configured timezone, never dropped and never sent early.

## Impact analysis

**No migration.** `policy_versions.body` is `JSONB` and the new fields all have defaults, so
existing immutable rows deserialize unchanged. `policy_versions` is guard-triggered (only
`status`/`approved_by`/`approved_at` are updatable), which is why adding defaulted fields rather
than rewriting rows is the only workable approach.

**No new API surface.** `PolicyBody` appears in **zero** OpenAPI schemas — verified against the
committed snapshot, not assumed. No endpoint accepts or returns it today.

**OpenAPI and TS are still regenerated**, because `info.version` carries `CONTRACT_VERSION`.

**Known side effect, disclosed rather than discovered later:** the seeded policy's
`content_hash` is a digest of the canonical body, so adding fields changes it. Tests recompute
the hash and therefore stay valid, but the literal `sha256:e6e54ac6b44bdb3901e6569b6ac41bb8b2b1c422e475c843cfe14c99f7b71b48`
recorded in `docs/phase-reports/wave1-handoff.md` becomes stale and is corrected in the same
change. The post-CCR-004 value is `sha256:cfbb802e0775acc119bbaa5956fedfe2b10abecf9ee18ddc111eab0e80ae4fca`.

(`i1.md` and `wave2a.md` were checked and carry no hash literal, so nothing there needed
correcting — the stale copy was only in the Wave 1 handoff.)

## Considered and found *not* to require a change

| Candidate | Why not |
|---|---|
| A new `scheduled_jobs` column for the due reason | `payload` is JSONB and already carries `step_no`. |
| A follow-up-specific `BlockCode` | `follow_up` is already a policy action and the existing codes cover every stop condition. |
| Exposing policy over HTTP | Nothing in Wave 2B reads policy through the API. A later CCR can add it. |

## Breaking?

No. Five additive, defaulted fields on a JSONB-backed DTO. `0.3.0 → 0.4.0`.
