# CCR-002 — `DomainMetric.value` must be `float | None`

Status: **FILED, NOT APPLIED.** Awaiting the user's decision.
Filed: 2026-10-17 by the Lead, from a Lane C finding during the Wave 1 resume.
Affects contract **C2** (domain DTOs). Contract version would move `0.1.0` → `0.2.0`
(can ship together with CCR-001, which is also pending).

## What

Change the frozen `kb_contracts.domain.DomainMetric.value` from `float` to `float | None`,
aligning it with `kb_contracts.providers.SEOMetric.value`, which is already `float | None`.

## Why — the two sides of the same metric disagree

| DTO | Field | Nullable? |
|---|---|---|
| `SEOMetric` (provider side, C5) | `value: float \| None` | yes — carries `# None = unavailable; never fabricate (ADR-0015)` |
| `DomainMetric` (persisted side, C2) | `value: float` | **no** |
| `domain_metrics.value` (migration 001) | `numeric` | **nullable** |
| `DomainMetricRepository.record(value=...)` (seam) | `float \| None` | yes |

So the database column, the provider DTO and the repository signature all admit "fetched but
unavailable", and only the persisted DTO forbids it. A metric that was fetched and came back
unavailable is representable everywhere except in the DTO that represents a stored metric.

## Current workaround and why it is not good enough

Lane C stores `NULL` correctly and, on read-back, substitutes `float("nan")` to satisfy the
non-optional DTO. It is documented in `repos_core.py` with a `SEAM NOTE`. It is defensible as a
stopgap for exactly one reason: NaN fails every threshold comparison, so an unavailable metric
can never pass qualification. It fails safe against ADR-0015.

It is still wrong, verified by the Lead rather than assumed:

1. **It breaks JSON round-trip, silently.** Pydantic serializes NaN to `null`
   (`"value":null`). That output *looks* like a correct representation of "unavailable", but
   feeding it back raises a `ValidationError` against `value: float`. The DTO cannot round-trip
   through its own serializer.
2. **Strict JSON refuses it.** `json.dumps(nan, allow_nan=False)` raises
   `ValueError: Out of range float values are not JSON compliant`.
3. **`NaN != NaN`**, so any equality, dedupe, caching or set logic over metric values is
   quietly wrong.
4. **The type annotation lies.** A reader of `value: float` has no reason to expect NaN, and
   every consumer must remember an unwritten `math.isnan` check. That is precisely the kind of
   implicit contract this project uses typed DTOs to avoid.

`DomainMetricRepository.latest()` remains the authoritative three-state reader (key absent =
never fetched, `None` = fetched but unavailable, float = fetched with a value) and is what
qualification uses, so the DEFER path is correct today regardless of this CCR.

## Blast radius right now: nil

Every API route is still a `501` stub, so nothing serializes `DomainMetric` anywhere in the
codebase. Verified by inspection. The defect is contained to one repository return value.

**This must be resolved before Lane B exposes metrics through the API.** Once a route returns a
`DomainMetric`, item 1 above becomes a live wire-format bug rather than a latent one.

## Recommendation

Approve. It is a one-line change to a frozen DTO plus a `SEAM NOTE` removal, it makes the two
metric DTOs consistent, and it deletes a NaN sentinel rather than building on it. Bundle it with
CCR-001 so the contract version moves once.

## Lead's note on how this was missed

When the Lead confirmed "no contract change is required" before this wave, the check was made
against `SEOMetric` (provider side, already nullable) and not against `DomainMetric` (persisted
side). The two differ, and only the provider side was verified.
